# 架构与行业改造

以下要求面向执行建站的 Agent；文中的「我」指正在请求建站的使用者。复用当前对话中已明确的回答、授权和完成状态。

参考常量基于 AIHOT 提交 `8d5a39bb47c917616798a3fdd71688a80f6c9b6c`；改代码前核对当前版本。来源见 [来源与许可](provenance.md)。

## 二、实现策略：在原项目上改造

1. 如果当前工作区已经是 AIHOT 或它的衍生项目，读取现有文件和未提交改动，沿用该项目，不覆盖已有工作。如果还没有项目，在独立目录克隆上游；不要未经授权替我创建远端仓库或推送代码。
2. 检查并记录所用 commit、Node 版本、数据库版本及依赖锁文件。默认使用开始时核实的上游版本，之后不要在开发过程中无提示地更新上游。上述参考提交可供对照，不是要求永久使用旧版。
3. 先读根目录 `AGENTS.md`、`README.md`，再读 `docs/customize.md`、`docs/architecture.md`、`docs/sources.md`、`docs/selection.md`、`docs/grouping.md`、`docs/deploy.md`。
4. 对照实际文件确认已有能力和本次差异。已存在且适用的代码直接复用，不为了展示工作量重写采集、事件归组、预算或后台。
5. 使用仓库锁定的依赖版本，不随意替换技术栈或升级大版本。默认不额外加入 Redis、Kafka、Elasticsearch、独立向量数据库、Kubernetes 或一组微服务。
6. 若无法访问仓库，先说明具体原因；尝试合法的现有本地副本或用户提供源码。缺少源码时可以做明确标注的兼容实现方案，但不能声称已忠实复用 AIHOT。
7. 保留 MIT 许可及版权声明，检查 `NOTICE` 中的第三方资产说明。使用我自己的品牌，不使用 AIHOT 的名称、Logo 或把它的运营数据当成我的内容。


## 三、保留这些架构边界

默认技术方案沿用仓库：Node.js 24 系列（参考版本要求至少 24.11）、TypeScript、npm workspaces、React Router 服务端渲染、Tailwind CSS、Fastify、PostgreSQL、pg-boss、Docker Compose。实际依赖以检出的锁文件为准。

目录职责：

| 位置 | 必须保留的职责 |
| --- | --- |
| `apps/web/` | 页面与交互，通过 HTTP 访问 API |
| `apps/api/` | 网站接口、公开接口、后台接口及相关输出 |
| `apps/worker/` | 定时采集、模型处理、事件归组、热度、刊物和维护任务 |
| `packages/backend/` | 数据访问和业务逻辑 |
| `packages/contracts/` | 跨进程共享的类型和契约 |
| `industry/` | 站名、品牌、分类、主题、信源、行业提示词和筛选门槛 |
| `database/migrations/` | 按顺序执行的数据库增量迁移 |
| `scripts/`、`tests/` | 初始化、评测、诊断和验证 |

关键规则：

- 前端不直接连接数据库，不暴露服务密钥，不直接调用模型。
- 读者打开页面、刷新列表或搜索内容，读取已处理结果，不启动一次新的模型推理。
- 模型调用发生在后台任务中。采集、判断和生成完成后，结果持久化，再由公开读取层提供给页面。
- 网站运行后由服务器上的 worker 自动处理新增资料，不要求站长每天在个人电脑跑完模型后手动上传结果。
- 所有公开出口通过 `packages/backend/src/publication/` 的共同规则读取，包括页面、RSS、API、MCP、分享图及站点地图。撤回、全文许可、公开范围等规则不在各出口各写一套。
- PostgreSQL 保存业务数据并承载 pg-boss 队列。优先沿用原项目的向量数组存储与余弦相似度实现；只有实际规模证明需要时再提出索引升级。
- 管理后台经过认证。默认公开内容匿名可读；新增用户体系或收费墙必须来自我的需求。


## 四、行业配置：把我的回答变成真实文件

1. `industry/site.ts`：站名、行业词、首页文案、关于页、抓取器名称、MCP 前缀等。公开站点 URL 从部署配置读取。
2. `industry/taxonomy.ts`：类别、类型、标签、机构及身份词表。标签必须来自允许集合；保留已有 schema 和归一化处理。
3. `industry/topics.json`：主题目录及其标签/机构映射。上线后保持分类 key、主题 slug、MCP 前缀稳定，需要变更时处理兼容。
4. `industry/sources.json`：首批信源。保留来源类型、级别、一手性、参与方式及全文开关等真实字段。
5. `industry/prompts/`：以原有任务和输入输出契约为基础，替换行业标准、举例、术语、读者画像与写作要求。
6. `industry/selection.ts`：筛选门槛。没有标注评测前先保留原始基线，并明确尚未校准。
7. `industry/features.ts`：非 AI 行业默认关闭模型榜和 Codex 重置监控；AI 行业也应按我的需要决定。
8. `industry/brand/`、`industry/pages/`：替换图标、品牌、报头、条款和隐私模板，检查页脚、SEO、分享图、RSS、后台等位置的一致性。

注意：`sources.json` 是种子数据，修改文件不等于覆盖数据库中已存在的信源。按现有 seed 行为核实结果；已有站点通过后台或明确的数据更新流程调整，不删除重建整个数据库。主题更新也要验证是否真正写入数据库。


## 五、采集与材料管道

沿用仓库已有 RSS、网页列表、JSON 接口、X、公众号和外部推送适配器。首批只启用我选定且具备接入条件的来源，其余保持可配置。

每条材料应能追溯：来源、原始 URL、外部 ID、标题、原文时间、发现时间、正文/摘要、语言、内容哈希、版本及处理结果。以实际 schema 为准，不另造一套平行数据库。

实现并验证：

- 重复抓取不重复建文章、重复计热度或无条件重复调用模型。
- 同一 URL 内容有实质变化时保留修订依据，按已有失效和重处理规则运行。
- 不同来源报道同一件事时保留各自报道，由事实归组解决，不能直接丢掉出处。
- 标题、摘要不足时按已有逻辑获取正文；处理清洗、超时、限流、无效日期和解析失败。
- 保留发布时间、发现时间与公开时间的区别；历史补采和新信源存量不冒充今天的新消息。
- 每个来源可试抓、暂停、设置频率并查看最近成功/失败原因。
- 保留仓库已有 URL 校验、请求约束和 HTML 清洗，不让采集器或图片代理变成任意内网访问入口。
- 付费采集未配置时说明不可用原因，网站其它功能仍可运行。不得用虚构数据填充真实新闻流来掩盖失败。
