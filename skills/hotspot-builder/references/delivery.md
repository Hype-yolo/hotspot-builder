# 模型、验证与交付

以下要求面向执行建站的 Agent；文中的「我」指正在请求建站的使用者。复用当前对话中已明确的回答、授权和完成状态。

参考常量基于 AIHOT 提交 `8d5a39bb47c917616798a3fdd71688a80f6c9b6c`；改代码前核对当前版本。来源见 [来源与许可](provenance.md)。

## 九、模型、预算和故障恢复

开发 Agent、网站使用的语言模型、网站使用的 Embedding 模型是三个不同角色。运行网站不需要把开发 Agent 一直开着；服务器通过 API 调用所配置的模型。

默认通过 OpenAI 兼容接口配置 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`。先用一个经过兼容性验证的文本模型跑通，保留按步骤切换的能力，再按实际效果决定是否多模型分工。

检查实际支持的路由，包括预筛、评分、内容理解、简写、结构化、归组、复核、事件综述、刊物和翻译。模型名称不能凭记忆写死；核对提供商可用 ID、JSON 输出、超时和服务商特定参数。不要把作者的参考分工作为所有使用者必须购买的套餐。

Embedding 通过单独的 `/embeddings` 接口配置。它不是每台云服务器自带的功能，也不要求网站与模型提供商处于同一家云。

所有付费请求遵守现有回执机制和预算熔断：

- 发起前记录任务身份，收到结果先保存，再用于业务处理。
- 已确认成功的相同请求重试应复用结果。
- 结果不明、解析失败、提供商明确拒绝等状态分别处理，不一律无限重发。
- 保留有限重试、退避、人工核对及进程优雅关闭；已授权的正常重试不反复询问我。
- 不宣称 exactly-once 计费或绝对不会重复扣费。外部服务已扣费但响应丢失时，系统可能无法确定结果。
- 每分钟、每小时、每天的调用次数上限和人民币支出上限不是一回事。准确解释现有预算功能覆盖什么。
- 我要求明确金额上限时，先检查提供商可用额度限制；若增加应用金额限制，计入并发预留和失败重试等因素，区分预估与真实账单。

预算估算基于实际小批量运行：记录原始条数、各步骤调用次数、缓存复用、输入输出 token、Embedding 用量及付费采集次数，再按已核实单价估算月费用区间。明确估算假设，分别列模型、采集、服务器和存储。不凭一句「每天 100 条」给出无依据的精确价格。

在缺少密钥或费用授权时，使用本地假服务/夹具验证流程，界面标明演示数据；不能把模拟成功当成真实模型效果验证。生产页面浏览不新增模型调用应可用回执计数证明。


## 十、页面与后台交付要求

沿用原有路由和成熟交互，按我的需求调整布局。至少完成已选模块的真实数据连接：

- 首页：精选和当前热点，明确区分它们的排序依据。
- 全部动态：分类筛选、搜索和分页/加载更多。
- 热点及事件详情：聚合标题、综述、发展过程和来源报道。
- 报道详情：标题、摘要、来源、时间、原文链接，全文按许可显示。
- 主题、日报及已启用的周报月报页面。
- 关于、必要政策页面、RSS/API/MCP 接入说明。

手机端和桌面端都检查文字、图片、长标题、导航、空状态、加载错误及无结果搜索。核心交互必须可用，不能用一排无效按钮代替功能。

后台至少保留：信源配置与试抓、材料处理诊断、预筛/两次评分结果、模型路由、回执与用量、任务状态、失败重试、人工选入/撤回及归组修正、刊物管理、精选评测和预算设置。复用已有页面，不为每个底层字段额外新造页面。

新行业尚无数据时，正确展示空状态；需要演示时使用隔离的数据集。禁止把 AIHOT 的线上新闻数量、访问量、性能或运营效果冒充这个新站的实际结果。


## 十一、开发顺序与验证证据

按依赖推进，不要把所有功能写完后才首次运行：

**阶段 A：确认项目能启动。** 安装锁定依赖，配置独立数据库，执行迁移和 seed，启动 api、worker、web。开发与测试时显式关闭采集、真实模型调用、外部推送和索引提交；不要直接沿用 `.env.example` 中默认开启的采集与模型开关。

**阶段 B：替换行业配置并验证页面。** 将问答结论落到文件和数据库，检查分类、信源、提示词、品牌及页面实际效果。先跑已有检查，修复本次改造引起的错误。

**阶段 C：验证完整处理链。** 用隔离的本地样本和假模型服务走真实业务代码，证明从采集/导入到公开页面的持久化链路工作。不要为演示另写一套跳过评分和归组的捷径。

**阶段 D：有限真实试运行。** 密钥、接入条件和小批量费用授权具备后，对首批约 3–5 个已选来源和约 20–50 条材料运行真实流程；实际规模服从我的预算。首批验证完成前，不自动对所有历史内容全量回灌。

**阶段 E：校准。** 先让我评判少量真实样本，明确误选与漏选原因；准备原格式的标注文件和评测命令。正式评估建议积累 100–200 条、包含难例和留出集。只有我标注或明确确认的结果才算人工 gold，不能把你自己的判断伪装成人工标注。

**阶段 F：交付或部署。** 完成本地可用交付；如果已有明确部署授权，按下一节执行。真实模型效果、公开域名访问等尚未验证时标明具体层级，不把整个任务粗暴标成「完成」。

优先复用已有测试，新增测试只覆盖本次改变的重要行为。至少核对以下场景：

| 场景 | 预期证据 |
| --- | --- |
| 同一条输入重复导入 | 不增加重复文章、不重复使用已成功回执 |
| 两次独立评分 | 有两个独立调用身份，正确按总分与门槛比较 |
| BLOCK / UNKNOWN | 前者不公开，后者按原流程继续 |
| 两家报道同一发布 | 同一事实，保留两个来源 |
| 同一事件的直接后续 | 新事实关联既有事件，原始报道仍可追溯 |
| 同公司不同事情 | 不仅凭主体相同而错误合并 |
| 多话题日报 | 不将多个事件串成一个大组 |
| 来源内重复报道 | 不被计成多个独立热度参与者 |
| 时间推进 | 24 小时贡献减半，窗口外证据按规则不计 |
| 模型返回非法 JSON / 超时 / 429 | 有错误记录和有限恢复，不伪装成功 |
| Embedding 未配置或维度变更 | 降级状态明确，不混算不兼容向量 |
| 任务重复执行或 worker 重启 | 持久化状态可恢复，不重复出版或推送 |
| 管理员修改标题或归属 | 后台任务遵守人工覆盖规则 |
| 内容撤回 | 网页、RSS、API、MCP 和相关衍生内容一致处理 |
| 访问公开页面和搜索 | 模型回执数没有因浏览而增加 |
| 未登录访问后台 | 正确拒绝，不泄露密钥与管理能力 |

参考命令如下，先依据实际版本核实可执行入口。测试必须使用独立空库，名称以 `_test` 或 `_ci` 结尾，不对生产库运行测试迁移：

```bash
npm run typecheck
DATABASE_URL=<独立测试库连接> node scripts/migrate.ts
DATABASE_URL=<独立测试库连接> npm test
npm run build -w @aihot/web
node --test apps/web/tests/*.test.ts
node scripts/smoke.ts --base http://localhost:3000
```

这些命令中的连接字符串是说明占位符，不要原样执行。站点 smoke 要在服务真实启动后运行。数据库测试中的模型和外部服务使用本地假服务；真实付费试运行单独执行并记录。

检查选择和关系评测脚本的现有用法，复用 `scripts/eval-selection.ts` 与 `scripts/eval-relations.ts`。不要用结构化输出通过率代替选得准不准，也不要用假服务测试通过率代替真实模型效果。


## 十二、部署和日常运行

默认交付 Docker Compose，保留 db、一次性 setup、api、worker、web。只有实际需要且没有现有代理时才使用 Caddy；已有 Nginx 就接入现有代理方案。

部署前核实实际环境、可用内存、磁盘、数据库、域名、端口和现有业务。参考项目建议 2 核 4 GB，包括构建需求；共享服务器按剩余资源评估，不能当作空闲专用机。必要时在其它环境构建镜像后部署，或明确容量限制。

满足以下要求：

- 数据库、媒体文件和相关状态使用持久化存储。
- 管理员密码、会话密钥、数据库密码等使用安全随机值；不提交 `.env`，不把密钥写进前端、日志、截图和公开交付文档。
- API、数据库等内部服务只暴露需要的边界；代理、HTTPS 和 `SITE_URL` 配置保持一致。
- 已有服务更新前备份并按原项目要求安排迁移和进程停止顺序；不在旧 worker 仍写数据时盲目迁移。
- 给 worker 足够的优雅退出时间，避免强杀正在等待付费响应的任务。
- 定时任务有运行记录，失败和长时间无新内容可以诊断；告警目标须经我的需求确认。
- 提供数据库备份、恢复、更新和回滚步骤。可行时在独立环境做一次恢复验证，不只检查备份文件存在。
- 不删除数据库卷、不覆盖无关项目、不重启整个共享服务器来解决局部问题。

部署是指让网站在真实目标环境提供服务。未获得该目标的部署授权时先完成本地运行、部署配置和发布前验证；已有明确授权就执行，不重复询问相同权限。域名、服务器、付费服务和发送目标不得自行扩大。


## 十三、最终交付

在项目内交付实际可运行代码以及必要说明，不额外生成大量互相重复的文档。至少包含：

1. 项目目录与启动入口，所用上游提交和本次主要改动。
2. 我的行业配置、完整生产提示词、分类与信源设置；简要说明未来分别在哪里修改。
3. 不含凭据的 `.env.example`，说明哪些必填、哪些可选、未配置时缺少什么功能。
4. 本地地址、后台入口、已授权部署的地址及实际验证状态。凭据通过私有方式查看，不在公开文档展示。
5. 一条真实材料从入库到评分、写作、归组和公开展示的可追溯示例；未做真实试运行时，明确注明是模拟示例。
6. 自动化检查与页面验证结果，已验证的失败恢复路径。
7. 实际用量或带假设的成本估算，剩余预算/凭据/标注缺口。
8. 简短运维说明：启动、停止、看日志、加信源、改标准、切模型、备份恢复和更新。

最终用普通话告诉我：已经能做什么、我到哪里使用、哪些真实运行条件还缺失。不要以「已写好代码」代替已启动，以「有界面」代替有真实数据流程，以「测试通过」代替精选质量已经达到运营标准。
